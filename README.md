# PrimeFit frontend

A Next.js App Router frontend for PrimeFit, a personal menswear discovery experience. This repository intentionally contains no fake product catalogue. Product cards appear only when the backend returns matching products for a user's style profile.

## 1. Run locally

Requirements: Node.js 20.9+ (Node 22+ recommended).

```bash
cp .env.example .env.local
npm install
npm run dev
```

Open http://localhost:3000.

Set `NEXT_PUBLIC_API_BASE_URL` in `.env.local` to your existing backend URL. Keep the trailing slash off. The website can render while the backend is offline, but login, database syncing, contact submission, and matched product results require the corresponding backend endpoints.

## 2. Backend API contract

Route constants live in `lib/api.js`. Change them to match your existing API instead of creating duplicate endpoints unnecessarily.

| Method | Frontend route | Expected behaviour |
| --- | --- | --- |
| POST | `/api/auth/login` | Accept `{ email, password }`; return safe user data and preferably set a secure HttpOnly session cookie. |
| POST | `/api/auth/register` | Accept `{ name, email, password }`; validate and hash password server-side. |
| GET | `/api/auth/google` | Start Google OAuth on the backend and redirect to Google. |
| GET | `/api/auth/me` | Optional: return current authenticated user. |
| POST | `/api/auth/logout` | Optional: clear session. |
| POST | `/api/style-profiles` | Save or update a style profile; return `{ id }` or `{ profileId }`. Support anonymous profile IDs if desired. |
| GET | `/api/style-profiles/:id` | Optional: load a saved profile. |
| POST | `/api/products/matched` | Accept `{ profile, profileId? }`; return `{ products: [...] }` or an array. Return only relevant, real products. |
| POST | `/api/contact` | Validate and store/forward contact messages. Add rate limiting and spam protection. |

Suggested product response shape:

```json
{
  "products": [
    {
      "id": "your-product-id",
      "title": "Product title from the real catalogue",
      "brand": "Brand name",
      "price": 1299,
      "currency": "₹",
      "imageUrl": "https://...",
      "imageAlt": "Accurate product image description",
      "affiliateUrl": "https://approved-tracking-link...",
      "category": "Shirts",
      "matchReason": "Matches your colour and fit preferences"
    }
  ]
}
```

Do not expose affiliate network credentials in frontend code. Fetch/import Cuelinks catalogue data and tracking URLs on the backend, subject to the network's rules. The frontend only receives the product data needed to display a product and its approved tracking link.

### Authentication notes

- The Google button redirects to `GET /api/auth/google`; the backend must implement OAuth and redirect back to the frontend's configured callback route.
- Prefer secure, HttpOnly, SameSite cookies over storing long-lived bearer tokens in localStorage. The example stores a returned token only for compatibility with a backend that requires it; remove that code if your backend uses cookie sessions.
- If frontend and backend use different origins, configure exact CORS origins and credentials on the backend. Use HTTPS in production.
- Enforce server-side validation, password hashing (Argon2id/bcrypt), rate limiting, CSRF protections where appropriate, email verification and account recovery.

## 3. Style profile behaviour

The profile is split into four short steps and fields are optional unless the user chooses them. The browser keeps a local copy in `localStorage`; the form also attempts to save it to the backend. If the backend is unreachable, it tells the user the profile is only stored on that device rather than pretending database storage succeeded. `localStorage` is not a secure database and can be cleared by the user.

The current fields are a useful starting point, not a claim that every body or sizing factor can be inferred. Add questions only when the matching logic actually uses them. Avoid asking for 100 fields upfront; progressive, relevant questions usually produce better completion rates.

## 4. SEO and Cuelinks review readiness

Included:
- Server-rendered homepage copy and occasion links.
- Page titles, descriptions, canonical URLs and Open Graph metadata.
- `robots.txt` and `sitemap.xml` generated by App Router.
- WebSite JSON-LD on the homepage.
- Public About, Contact, Privacy Policy, Terms and Affiliate Disclosure pages.
- Accessible labels, keyboard focus styles, reduced-motion support, responsive layout and no fabricated products.

Before publishing:
1. Set `NEXT_PUBLIC_SITE_URL` to your real HTTPS domain.
2. Replace policy copy as needed to match the actual company, data flows, jurisdiction and services. The policy pages are a starting draft, not legal advice.
3. Ensure Contact submissions really work and provide a monitored contact route. Do not publish invented contact details.
4. Verify the real Cuelinks publisher requirements, website ownership, disclosure wording and any rules for product feeds/deep links. Approval is not guaranteed by the design.
5. Test mobile, keyboard navigation, broken links, page speed, metadata, sitemap and production build.
6. Ensure the backend returns only current, approved product records and valid tracking links.

## 5. Main routes

- `/` — SEO-friendly homepage and occasion navigation
- `/my-style` — profile wizard
- `/discover` — matching products returned by backend
- `/login` — Google sign-in redirect and email/password login or account creation
- `/about`, `/contact`, `/privacy-policy`, `/terms`, `/affiliate-disclosure` — trust and legal pages
